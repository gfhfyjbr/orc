# PLAN: внешняя orchestration для OpenCode через tmux

## 1. Жесткие ограничения

Новая рамка задачи такая:

- код самого OpenCode менять нельзя;
- нужно использовать только то, что OpenCode уже умеет сейчас;
- сабагенты должны запускаться именно через `tmux`;
- orchestration должна жить снаружи OpenCode, как внешняя обвязка;
- main agent и subagents = это отдельные запуски существующего OpenCode, а не новые встроенные режимы.

Из этого следует главный вывод:

**нельзя проектировать встроенный orchestrator внутри OpenCode. Нужно проектировать внешний tmux-based runtime, который запускает несколько экземпляров OpenCode и связывает их через файлы, промпты и terminal automation.**

## 2. Что здесь значит orchestration

В этом варианте orchestration = это внешний управляющий слой, который:

- поднимает один экземпляр OpenCode как main agent;
- поднимает дополнительные экземпляры OpenCode как subagents в отдельных `tmux` pane/window;
- передает каждому агенту отдельный prompt и набор файлов-контрактов;
- следит за их статусом;
- собирает результаты из workspace;
- возвращает результаты main agent'у через следующий prompt;
- позволяет main agent продолжить работу после завершения сабагентов.

То есть orchestration тут не "внутри OpenCode", а **вокруг OpenCode**.

## 3. Базовая идея

Самая здравая схема такая:

- `tmux` используется как runtime и диспетчер terminal sessions;
- каждый агент = отдельный `opencode` процесс в своей pane;
- orchestration glue делается shell-скриптами;
- shell-скрипты общаются с агентами через `tmux send-keys`;
- `spec.md` хранит роль агента, шаблон поведения и конкретное задание на run;
- если нужен долговечный след, агент дополнительно пишет файлы-артефакты, но оперативное взаимодействие идет через shell + `send-keys`.

Коротко:

1. `tmux` дает изоляцию, живые сессии и наблюдаемость;
2. shell-скрипты дают control plane;
3. промпты задают поведение агентов;
4. `spec.md` и при необходимости result-файлы дают общую память между шагами.

## 4. Почему `tmux`, а не просто много процессов

Потому что для TUI это самый удобный substrate:

- можно держать main agent и сабагентов одновременно живыми;
- можно визуально переключаться между pane и смотреть прогресс;
- можно делать `send-keys` для bootstrap действий;
- можно делать `capture-pane` для диагностики;
- можно делать `pipe-pane` в лог-файлы;
- можно переживать detach/attach без потери сессии;
- можно хранить все агентные рантаймы в одном tmux socket/session.

Если делать без `tmux`, будет заметно хуже:

- сложнее операторский дебаг;
- сложнее attach/detach;
- сложнее видеть параллельную работу;
- сложнее вручную вмешаться в конкретного агента.

## 5. Главный архитектурный принцип

**tmux + shell-скрипты = основной control plane orchestration.**

Нельзя делать архитектуру, где main agent "получает ответ от сабагента" через то, что кто-то глазами прочитал текст в pane.

Нужно разделить два канала:

### Канал 1: human-visible terminal stream

Нужен для:

- live наблюдения;
- дебага;
- ручного вмешательства;
- UX в TUI.

Источник:

- сам экран pane;
- `tmux capture-pane`;
- `tmux pipe-pane`.

### Канал 2: script-driven handoff

Нужен для:

- передачи результатов назад main agent'у;
- запуска follow-up prompt'ов;
- оркестрации через `.sh`-скрипты;
- автоматической пересылки контекста между pane.

Источник:

- `tmux send-keys`;
- shell-скрипты вроде `spawn-agent.sh`, `send-task.sh`, `resume-main.sh`;
- при необходимости - файлы в общем workspace.

Для живой orchestration source of truth = shell-скрипты + tmux state. Файлы нужны как долговечная память, шаблоны ролей и резервный след.

## 6. Общая схема компонентов

### 6.1 Внешняя shell-обвязка

Это не часть OpenCode. Это внешняя обвязка, например:

- `orchestrate.sh`;
- `spawn-agent.sh`;
- `send-task.sh`;
- `resume-main.sh`;
- `collect-review.sh`;
- или полу-ручной режим, где человек и tmux-команды выполняют orchestration.

Задачи shell-обвязки:

- создать структуру каталогов для run'ов;
- поднять `tmux` session;
- открыть pane/window для main agent и subagents;
- заинжектить стартовые промпты;
- пересылать контекст между агентами через `send-keys`;
- при необходимости читать/писать вспомогательные файлы;
- передавать main agent'у результаты следующими prompt'ами;
- делать retry/cancel при необходимости.

### 6.2 Main agent

Это обычный OpenCode, просто запущенный в одном из `tmux` pane.

Его роль:

- принять пользовательскую задачу;
- спланировать, нужны ли сабагенты;
- сформулировать задания для них;
- после их завершения синтезировать результат;
- продолжить reasoning и ответить пользователю.

Важно: сам main agent не обязан технически спавнить tmux. Это делает shell-обвязка. Но main agent может логически решать, каких сабагентов создать.

### 6.3 Subagent

Это тоже обычный OpenCode, запущенный в другом `tmux` pane.

Его роль:

- выполнить узкую подзадачу;
- не выходить за свой scope;
- записать статус и итог в заранее оговоренные файлы;
- остановиться.

### 6.4 Shared workspace

Общий каталог нужен не как единственный канал связи, а как место для шаблонов ролей, промежуточных заметок, артефактов и резервного следа.

Пример:

```text
.orchestrator/
  sessions/
    session-001/
      inbox/
      outbox/
      runs/
        main/
          brief.md
          notes.md
        run-001/
          spec.md
          status.json
          handoff.md
          result.json
          transcript.log
        run-002/
          spec.md
          status.json
          handoff.md
          result.json
          transcript.log
```

## 7. Как main agent создает сабагентов без модификации OpenCode

Так как OpenCode менять нельзя, схема должна быть только через уже существующие поведения:

1. main agent получает задачу;
2. main agent в ответе формирует план и список subagent tasks;
3. shell-скрипт читает этот план из файла или копипастного блока;
4. shell-скрипт создает новые `tmux` pane;
5. shell-скрипт запускает в них новые экземпляры `opencode`;
6. shell-скрипт отправляет каждому экземпляру стартовый prompt через `tmux send-keys`;
7. сабагенты работают;
8. shell-скрипт передает main agent'у их выжимку или follow-up instructions тоже через `tmux send-keys`;
9. если нужно долговременное хранение, агент дополнительно пишет результат в файлы.

То есть реальное создание сабагентов делает внешняя shell-обвязка, но решение о создании может исходить от main agent.

## 8. Минимальный orchestration protocol

Раз менять OpenCode нельзя, протокол должен быть максимально тупой и надежный: `tmux send-keys` + shell-скрипты + опциональные файлы.

### 8.1 Для каждого сабагента нужны 3 слоя

#### Слой 1: роль через `spec.md`

`spec.md` - это не просто ТЗ на конкретный run, а template профессии агента + конкретизация текущей задачи.

То есть в `spec.md` лежит:

- кто агент по роли;
- как он должен думать;
- какие у него обязанности;
- какие ограничения у роли;
- что именно он делает в текущем run.

#### Слой 2: shell handoff

Основное общение между агентами идет через `.sh`-команды, которые отправляют follow-up prompt'ы в нужную pane.

Например:

- `spawn-agent.sh reviewer`
- `send-task.sh run-001`
- `resume-main.sh run-001`
- `request-review.sh run-003`

#### Слой 3: optional artifacts

Если нужно сохранить результат между шагами или дать агенту большой контекст, используются файлы.

### 8.2 Для каждого сабагента полезны такие файлы

#### `spec.md`

Человеко-читаемый template роли + ТЗ для конкретного сабагента.

Содержит:

- `run_id`;
- роль и профиль поведения;
- цель;
- контекст;
- ограничения;
- ожидаемый формат результата;
- инструкции, кому и как отдать результат дальше.

#### `status.json`

Промежуточный статус, если нужен watchdog или долгий run.

Даже если OpenCode сам по себе не умеет стримить structured status, его можно прямо попросить в промпте периодически переписывать этот файл.

#### `handoff.md`

Человеко-читаемая выжимка, которую потом shell-скрипт или main agent может быстро скормить дальше.

Нужна для:

- быстрого просмотра;
- ручного дебага;
- удобного чтения main agent'ом;
- передачи результата через следующий `send-keys` prompt.

#### `result.json`

Машинно-читаемый итог, если нужен формальный follow-up, агрегация или повторный запуск.

Даже если main agent затем будет читать `handoff.md`, иметь рядом `result.json` полезно для shell-обвязки и дальнейшей автоматизации.

## 8.3 Надёжная доставка промптов через send-keys

`tmux send-keys` — это эмуляция набора текста в терминал. Без дополнительных мер это хрупкий механизм, который может потерять или исказить данные.

### Проблемы голого send-keys

- **Timing:** нет гарантии, что OpenCode готов принять ввод. Если TUI рендерится или агент думает, текст может улететь в никуда.
- **Многострочные промпты:** последовательные `send-keys` + `Enter` могут отправить первую строку как отдельный промпт до прихода остальных.
- **Спецсимволы:** кавычки, скобки, unicode, backticks могут быть интерпретированы tmux или shell некорректно.
- **Нет acknowledgment:** после `send-keys` нельзя узнать, получил ли OpenCode текст и начал ли обрабатывать.

### Обязательные меры для MVP

#### 1. Буферизованная отправка вместо построчного send-keys

Промпт целиком записывается в tmux buffer и вставляется одной операцией:

```bash
# НЕ ТАК:
tmux send-keys -t "$PANE" "строка 1" Enter
tmux send-keys -t "$PANE" "строка 2" Enter

# А ТАК:
PROMPT="$(cat .orchestrator/sessions/$SID/runs/$RUN_ID/prompt.txt)"
tmux set-buffer -b prompt "$PROMPT"
tmux paste-buffer -b prompt -t "$PANE"
tmux send-keys -t "$PANE" Enter
```

Это гарантирует, что весь текст вставляется атомарно, без разрыва на строки.

#### 2. Проверка готовности pane перед отправкой

Перед `send-keys` / `paste-buffer` shell-скрипт должен убедиться, что OpenCode готов принять ввод:

```bash
wait_for_prompt() {
  local pane="$1"
  local timeout="${2:-60}"
  local elapsed=0

  while [ "$elapsed" -lt "$timeout" ]; do
    # Проверяем, что в последних строках pane есть маркер готовности ввода
    local content
    content=$(tmux capture-pane -t "$pane" -p -S -5)

    # OpenCode показывает input prompt когда готов
    if echo "$content" | grep -qE '(>|❯|\$|input)'; then
      return 0
    fi

    sleep 1
    elapsed=$((elapsed + 1))
  done

  return 1  # timeout — pane не готов
}
```

Конкретный маркер готовности зависит от UI OpenCode и должен быть определён экспериментально при первом запуске.

#### 3. Экранирование спецсимволов

Все промпты перед отправкой через buffer должны проходить санитизацию:

```bash
sanitize_prompt() {
  # tmux paste-buffer вставляет raw text, но на всякий случай
  # убираем управляющие последовательности, которые могут сломать TUI
  printf '%s' "$1" | tr -d '\033'
}
```

#### 4. Промпт-файлы как source of truth

Каждый промпт, который отправляется агенту, **должен быть предварительно записан в файл**:

```text
.orchestrator/sessions/session-001/runs/run-001/prompt.txt
```

Это даёт:
- возможность retry с тем же промптом;
- аудит-лог того, что именно получил агент;
- дебаг, если агент повёл себя неожиданно.

## 9. Почему не надо пытаться тащить все через stdout pane

Потому что это хрупкая хрень:

- ANSI;
- прерывания;
- лишний текст;
- промежуточные рассуждения;
- артефакты TUI;
- сложно понять, где именно финальный ответ;
- трудно восстанавливаться после рестарта.

Поэтому stdout/pane text используется только как:

- live progress;
- debugging channel;
- страховка, если агент повел себя странно.

А рабочая orchestration-коммуникация - через `send-keys`, shell-скрипты и при необходимости через handoff/result-файлы.

## 10. Рекомендуемая tmux-топология

Главная рекомендация по layout:

- самый левый pane должен быть выделен только под orchestrator/main-agent interaction;
- это фиксированная управляющая зона, куда приходят follow-up prompt'ы, планы и handoff от сабагентов;
- все правое пространство должно быть рабочей зоной для subagent pane;
- пользователь общается в первую очередь с левым pane, а правые pane живут как параллельные исполнители.

Идея в том, что layout должен визуально подчеркивать иерархию:

- слева - мозг и точка управления;
- справа - временные помощники, которых orchestrator поднимает, слушает и гасит.

### Вариант A: одна session, много pane

Подходит для первых версий.

Например:

- левый фиксированный pane - orchestrator/main agent;
- правый верхний pane - researcher #1;
- правый средний pane - researcher #2;
- правый нижний pane - reviewer;
- при необходимости дополнительные правые pane создаются и уничтожаются динамически.

Плюсы:

- пользователь всегда знает, куда писать;
- главный поток работы не теряется среди сабагентов;
- удобно наблюдать за помощниками справа;
- удобно для небольшого числа сабагентов.

Минусы:

- при большом числе pane становится помойкой.

**Жёсткий лимит для MVP: максимум 3 одновременных subagent pane.**

При большем числе pane:
- терминал становится нечитаемым;
- каждый pane получает слишком мало строк для нормальной работы TUI;
- shell-обвязка усложняется без реальной пользы.

Если задача требует больше 3 сабагентов — shell-обвязка должна использовать **очередь**: спавнить следующего агента только после завершения предыдущего. Параллелизм ограничен 3 слотами, остальные ждут.

### Рекомендуемый split для MVP

Самый практичный layout для старта:

1. сделать вертикальный split `25/75` или `30/70`;
2. левую колонку целиком отдать orchestrator pane;
3. правую колонку уже дробить горизонтально или сеткой под subagents;
4. новые агенты всегда рождать только в правой колонке;
5. main/orchestrator pane никогда не использовать под временных workers.

Это важно не только для UX, но и для automation:

- shell-скриптам проще всегда знать, что левый pane = main pane;
- follow-up prompt'ы всегда идут в одну и ту же цель;
- не возникает путаницы, какой pane является главным после нескольких spawn/kill циклов.

### Правила именования pane/window

Этим должен заниматься orchestrator, а не пользователь.

Рекомендуемые правила:

- window `main` - главный layout с левым orchestrator pane и правой worker-zone;
- window `logs` - технические логи и tail артефактов;
- window `review` - отдельная зона для reviewer/verifier, если ревью идет отдельно;
- pane title `orc:main` - фиксированный левый pane orchestrator/main agent;
- pane title `wrk:research:001`, `wrk:review:001`, `wrk:summary:001` - worker pane справа;
- pane title должен кодировать `role` и `run_id`, чтобы shell-обвязка могла быстро понять, кто есть кто.

Принцип:

- именование всегда генерирует orchestrator;
- пользователь не должен вручную придумывать имена pane;
- при убийстве и пересоздании worker pane orchestrator должен заново назначать имя по шаблону;
- левый pane всегда сохраняет одно и то же стабильное имя, чтобы в него безопасно слать follow-up prompt'ы.

### Вариант B: одна session, отдельные windows

Подходит лучше для реальной работы.

- window `main` - main agent;
- window `workers` - несколько subagent pane в правой рабочей зоне;
- window `logs` - tail файлов / orchestration shell;
- window `review` - reviewer/verifier runs.

### Вариант C: отдельная session на крупную ветку

Нужно только если ветки очень долгие или их очень много.

Для MVP не обязательно.

## 11. Жизненный цикл run

Для каждого subagent run:

1. shell-скрипт создает каталог `runs/run-XYZ/`;
2. пишет туда `spec.md`;
3. поднимает pane;
4. запускает `opencode`;
5. инжектит prompt вида "прочитай spec и выполни задачу";
6. включает `pipe-pane` в `transcript.log`;
7. при необходимости ждет появления `status.json`;
8. ждет появления `handoff.md` и/или `result.json`;
9. отмечает run как completed/failed;
10. передает main agent'у следующий prompt через `tmux send-keys` с просьбой прочитать результат и продолжить.

## 12. Как именно main agent продолжает работу

Это ключевой момент.

Поскольку OpenCode нельзя допиливать, main agent продолжает работу через обычный следующий prompt в своей pane.

Важно зафиксировать отдельно:

- main agent не должен завершать свою работу после первого ответа;
- output сабагентов = это не финал сессии, а новый входной контекст для той же самой main-agent сессии;
- после получения результатов main agent должен иметь возможность ПРОДОЛЖИТЬ писать дальше в том же pane, в том же потоке работы;
- то есть orchestration должна не обрывать main agent, а докармливать его новыми данными и позволять ему продолжать reasoning и генерацию текста.

Схема такая:

1. subagent завершил `handoff.md` и/или `result.json`;
2. shell-скрипт проверил, что результат действительно есть;
3. shell-скрипт переключается на pane main agent;
4. shell-скрипт отправляет новый prompt примерно такого вида:

```text
Сабагент `run-001` завершил работу.

Прочитай файлы:
- `.orchestrator/sessions/session-001/runs/run-001/handoff.md`
- `.orchestrator/sessions/session-001/runs/run-001/result.json`

Используй их как входной контекст и продолжи выполнение общей задачи.
Если нужно, сформируй дополнительные подзадачи или подготовь финальный ответ.
```

5. main agent читает файлы своими обычными возможностями и продолжает reasoning.

То есть продолжение работы достигается не встроенным API, а тем, что main agent получает новый входной prompt через `send-keys` с указанием, какие артефакты импортировать.

Практический смысл:

- main agent может написать план;
- затем дождаться output от researcher/reviewer;
- затем в этой же сессии дописать обновленный план, финальный вывод или следующий набор subagent tasks;
- пользователю это должно выглядеть как непрерывная работа одного главного агента, а не как набор разорванных независимых запусков.

## 12.1 Main Agent Continuation Guarantee

Это поведение нужно считать обязательным свойством всей orchestration-схемы.

- main agent остается живым в одной и той же `tmux` pane на протяжении всей задачи;
- output сабагентов считается промежуточным материалом, а не точкой остановки main agent;
- shell-обвязка должна возвращать результаты сабагентов в main agent через follow-up `send-keys` prompt'ы;
- после каждого такого handoff main agent должен иметь возможность продолжить писать текст, строить следующий шаг, запускать новые сабагенты или выдавать финальный ответ;
- orchestration считается неудачной, если после output сабагентов main agent нельзя естественно продолжить в той же сессии;
- для пользователя все должно выглядеть как единый непрерывный поток работы одного главного агента с временным привлечением помощников.

## 13. Кто принимает решение о создании сабагентов

Есть два практичных режима.

### Режим 1: script-led

Внешний слой заранее знает паттерн:

- main agent;
- researcher;
- reviewer.

Плюс:

- проще всего сделать.

Минус:

- main agent меньше управляет системой.

### Режим 2: main-agent-led

Main agent решает, какие сабагенты нужны, и записывает план **в файл**, а не выводит в pane.

**Критически важно:** парсить structured data из terminal output (pane) — ненадёжно. LLM может выдать блок с вариациями формата, ANSI-артефактами, лишним текстом до/после блока. Поэтому:

- main agent **записывает план в файл** `.orchestrator/sessions/<sid>/plan.json`;
- shell-обвязка **читает файл**, а не парсит pane output;
- формат — **JSON**, а не YAML-like plain text (JSON проще парсить в shell через `jq`).

#### Формат файла плана

Main agent получает промпт, который просит его записать план в файл:

```json
{
  "session_id": "session-001",
  "tasks": [
    {
      "run_id": "run-001",
      "role": "researcher",
      "goal": "изучить tmux orchestration",
      "inputs": ["PLAN.md"],
      "deliverables": ["summary", "options", "risks", "recommendation"],
      "output_files": [
        ".orchestrator/sessions/session-001/runs/run-001/handoff.md",
        ".orchestrator/sessions/session-001/runs/run-001/result.json"
      ]
    },
    {
      "run_id": "run-002",
      "role": "reviewer",
      "goal": "проверить архитектурные риски",
      "inputs": [".orchestrator/sessions/session-001/runs/run-001/handoff.md"],
      "deliverables": ["verdict", "issues", "suggested fixes"],
      "depends_on": ["run-001"],
      "output_files": [
        ".orchestrator/sessions/session-001/runs/run-002/handoff.md",
        ".orchestrator/sessions/session-001/runs/run-002/result.json"
      ]
    }
  ]
}
```

#### Как shell-обвязка использует план

```bash
# Ждём появления файла плана
wait_for_plan() {
  local plan_file="$1"
  local timeout="${2:-120}"
  local elapsed=0

  while [ "$elapsed" -lt "$timeout" ]; do
    if [ -f "$plan_file" ] && jq empty "$plan_file" 2>/dev/null; then
      return 0
    fi
    sleep 2
    elapsed=$((elapsed + 2))
  done
  return 1
}

# Парсим и спавним
PLAN_FILE=".orchestrator/sessions/$SID/plan.json"
if wait_for_plan "$PLAN_FILE"; then
  TASK_COUNT=$(jq '.tasks | length' "$PLAN_FILE")
  for i in $(seq 0 $((TASK_COUNT - 1))); do
    RUN_ID=$(jq -r ".tasks[$i].run_id" "$PLAN_FILE")
    ROLE=$(jq -r ".tasks[$i].role" "$PLAN_FILE")
    # spawn + send-task для каждого run
  done
fi
```

#### Зависимости между run

Поле `depends_on` позволяет shell-обвязке понять порядок запуска:
- run без `depends_on` запускаются параллельно;
- run с `depends_on` ждут завершения указанных run;
- это простой DAG, который shell-обвязка обрабатывает линейно.

#### Промпт для main agent в этом режиме

```text
Если для задачи нужны сабагенты, запиши план в файл:
.orchestrator/sessions/session-001/plan.json

Формат — строго JSON. Используй структуру:
{
  "session_id": "...",
  "tasks": [
    {
      "run_id": "run-NNN",
      "role": "researcher|reviewer|explorer|summarizer|verifier",
      "goal": "...",
      "inputs": ["..."],
      "deliverables": ["..."],
      "depends_on": ["run-NNN"],  // опционально
      "output_files": ["..."]
    }
  ]
}

Если сабагенты не нужны, не создавай этот файл.
```

Это самый интересный режим, потому что:

- main agent реально становится "мозгом";
- shell-обвязка остается тупым исполнителем;
- план передаётся через файл, а не через хрупкий pane output;
- JSON парсится `jq` без костылей;
- код OpenCode при этом не меняется.

## 13.1 Модель ролей для сабагентов

У orchestrator должна быть двухуровневая модель ролей.

### Уровень 1: предустановленный пул ролей

Это основной режим работы.

Orchestrator заранее знает набор базовых ролей и умеет поднимать агентов по ним без дополнительных уточнений:

- `researcher`
- `explorer`
- `reviewer`
- `summarizer`
- `verifier`

Плюсы такого подхода:

- роли предсказуемые;
- проще писать `spec.md` шаблоны;
- проще shell-обвязке;
- проще пользователю понимать, кого вообще может вызвать orchestrator.

### Уровень 2: custom role по необходимости

Иногда предустановленных ролей не хватит. Тогда orchestrator может создать кастомную роль под конкретную задачу.

Но тут должно быть жесткое правило:

- orchestrator не создает custom role молча;
- сначала он обязан задать `question` с уточнениями или запросом подтверждения;
- только после ответа пользователя можно формировать новую роль и новый `spec.md` template для нее.

Причина простая:

- кастомная роль сильно влияет на поведение агента;
- без подтверждения можно породить лишнюю или не ту роль;
- это уже изменение самой схемы работы, а не просто очередной spawn стандартного worker.

Практически это должно выглядеть так:

1. orchestrator понимает, что стандартных ролей не хватает;
2. orchestrator задает один короткий `question` с предложением роли и тем, что она будет делать;
3. пользователь подтверждает или корректирует;
4. только после этого orchestrator создает custom role и спавнит агента.

## 13.2 Отдельный skill для orchestrator role-creation

> **Scope: v2. Не входит в MVP.**
>
> Для MVP предустановленных ролей (`researcher`, `explorer`, `reviewer`, `summarizer`, `verifier`) достаточно для 90%+ кейсов. Custom roles — это преждевременная абстракция, которая усложнит первую реализацию без реальной пользы. Вся секция 13.2 описывает дизайн для будущей версии.

Это нужно отдельно заложить в дальнейшую разработку.

Идея:

- у orchestrator должен быть отдельный skill, который он вызывает именно тогда, когда нужно создать новую кастомную роль;
- этот skill не нужен для обычных `researcher/reviewer/summarizer` сценариев;
- этот skill нужен как управляемый workflow для создания новой роли, нового role-template и нового `spec.md` профиля.

По документации OpenCode skills это должно быть оформлено как отдельный `SKILL.md` в каталоге вида:

- `.opencode/skills/orchestrator-role-factory/SKILL.md`

или другом корректном skill-name каталоге с тем же именем, что и в frontmatter.

### Что должен делать этот skill

Skill должен описывать полный flow создания новой роли:

1. понять, что предустановленного пула ролей недостаточно;
2. не создавать роль сразу;
3. сначала заставить orchestrator задать `question` пользователю;
4. собрать уточнение или подтверждение;
5. только после этого сформировать новую custom role;
6. описать для нее:
   - имя роли;
   - назначение;
   - границы ответственности;
   - ограничения;
   - ожидаемый output;
   - как эта роль общается с main agent;
7. подготовить шаблон `spec.md` для таких запусков;
8. вернуть orchestrator'у готовое role-definition описание, которое тот уже сможет использовать в orchestration.

### Что важно жестко прописать в skill

- custom role нельзя создавать без пользовательского подтверждения;
- если вопрос можно закрыть стандартной ролью, skill должен рекомендовать использовать стандартную роль;
- новая роль должна быть узкой и прикладной, а не расплывчатой;
- skill должен минимизировать proliferation ролей, чтобы orchestrator не наплодил зоопарк почти одинаковых агентов.

### Рекомендуемый шаблон skill frontmatter

С учетом OpenCode docs, в плане нужно предусмотреть skill примерно такого вида:

```md
---
name: orchestrator-role-factory
description: Create and validate custom subagent roles for the orchestrator after explicit user clarification or confirmation
compatibility: opencode
---
```

Дальше внутри skill уже описывается сам workflow.

### Как orchestrator должен использовать этот skill

Практический flow должен быть таким:

1. orchestrator пробует решить задачу через предустановленный пул ролей;
2. если понимает, что ни одна роль не подходит, он не импровизирует молча;
3. он вызывает skill `orchestrator-role-factory`;
4. skill заставляет его сформулировать `question` пользователю;
5. после ответа пользователя orchestrator получает от skill структуру новой роли;
6. только потом orchestrator создает `spec.md` и запускает кастомного агента.

То есть skill здесь нужен как guardrail и как единый протокол генерации новых ролей.

## 14. Что должна делать внешняя shell-обвязка

Минимальный набор обязанностей:

- создать tmux session/socket;
- запустить main agent;
- по команде или по плану поднять subagents;
- писать стартовые `spec.md`;
- отправлять bootstrap prompt в pane;
- логировать pane output через `pipe-pane`;
- отслеживать появление `status/result` файлов;
- по завершении сабагента слать main agent'у follow-up prompt;
- уметь cancel/retry вручную.

Важно: shell-обвязка не должна пытаться "думать за main agent". Она должна быть диспетчером команд, а не вторым мозгом.

## 15. Роли сабагентов

Поскольку все это строится только на промптах, роли лучше держать простыми и узкими.

Важно:

- по умолчанию orchestrator использует только предустановленный пул ролей;
- custom role - это исключение, а не норма;
- custom role допускается только после отдельного `question` и подтверждения пользователя.

### `researcher`

- ищет факты;
- сравнивает варианты;
- пишет выводы и trade-offs.

### `explorer`

- изучает локальный проект;
- собирает факты по кодовой базе;
- не предлагает лишних изменений вне scope.

### `implementer`

- нужен только если задача реально про код;
- в этой задаче не нужен, потому что пользователь запретил модификацию OpenCode.

### `reviewer`

- ищет дыры, риски, противоречия;
- проверяет, что proposal реалистичен;
- если задача про код, перед коммитом обязательно смотрит `git diff` и проверяет, что изменения соответствуют задаче.

### `summarizer`

- собирает несколько веток в компактную выжимку;
- полезен, если main agent не должен читать слишком много сырых результатов.

## 16. Контракт для файлов

### 16.1 `spec.md`

Пример:

```md

- role: researcher
- workspace: /path/to/project

## Output files
```

Структура:

- findings;
- options;
- recommendation;
- open questions.

### 16.5 Атомарность записи файлов

Агент может записать файл не полностью (прервался, упал, контекст кончился). Shell-обвязка может прочитать частично записанный файл и передать мусор main agent'у.

#### Обязательные правила для MVP

**1. Финальный маркер `DONE`**

Агент в конце работы должен создать файл-маркер, который появляется **строго после** всех остальных файлов:

```text
.orchestrator/sessions/session-001/runs/run-001/DONE
```

Содержимое маркера:

```json
{
  "run_id": "run-001",
  "status": "completed",
  "files": ["handoff.md", "result.json"],
  "completed_at": "2026-03-18T12:30:00Z"
}
```

Shell-обвязка ждёт **только `DONE`**, а не появление `handoff.md` или `result.json` по отдельности. Если `DONE` нет — run не считается завершённым.

Аналогично, при ошибке агент (или watchdog) создаёт:

```text
.orchestrator/sessions/session-001/runs/run-001/FAILED
```

```json
{
  "run_id": "run-001",
  "status": "failed",
  "reason": "agent timeout / agent error / missing deliverables",
  "failed_at": "2026-03-18T12:35:00Z"
}
```

**2. Порядок записи файлов**

Промпт агенту должен явно требовать порядок записи:

1. Сначала `status.json` (опционально, по ходу работы);
2. Затем `result.json`;
3. Затем `handoff.md`;
4. **В самом конце** — файл `DONE`.

Это обеспечивает, что к моменту появления `DONE` все артефакты уже записаны полностью.

**3. Shell-обвязка: polling только по маркеру**

```bash
wait_for_run() {
  local run_dir="$1"
  local timeout="${2:-300}"
  local elapsed=0

  while [ "$elapsed" -lt "$timeout" ]; do
    if [ -f "$run_dir/DONE" ]; then
      return 0
    fi
    if [ -f "$run_dir/FAILED" ]; then
      return 1
    fi
    sleep 2
    elapsed=$((elapsed + 2))
  done

  # Timeout — создаём FAILED маркер от имени watchdog
  cat > "$run_dir/FAILED" <<EOF
{
  "run_id": "$(basename "$run_dir")",
  "status": "failed",
  "reason": "timeout after ${timeout}s",
  "failed_at": "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
}
EOF
  return 1
}
```

### 16.6 Обновлённая структура каталога run

С учётом маркеров и промпт-файлов:

```text
.orchestrator/
  sessions/
    session-001/
      event-log.jsonl          # журнал событий orchestrator
      runs/
        run-001/
          spec.md              # роль + ТЗ
          prompt.txt           # фактический промпт, отправленный агенту
          status.json          # промежуточный статус (опционально)
          result.json          # машинно-читаемый итог
          handoff.md           # человеко-читаемая выжимка
          transcript.log       # pipe-pane лог
          DONE                 # маркер успешного завершения
          FAILED               # маркер ошибки (альтернатива DONE)
```

```text
- работай только в рамках `spec.md`;
- не расширяй scope;
- если нужно, обновляй `status.json`;
- в конце обязательно подготовь `handoff.md` и при необходимости `result.json`;
- не пытайся отвечать пользователю за всю систему;
- твоя задача - подготовить материал для main agent.

Твой итог должен быть кратким, проверяемым и пригодным для дальнейшего импорта main agent'ом.
```

## 26. Лучший практический сценарий для этой задачи

Для конкретно этой задачи логичный pipeline такой:

1. main agent получает задачу спроектировать orchestration;
2. main agent записывает `plan.json` с 2 сабагентами:
   - `researcher`: собрать варианты внешней orchestration через tmux;
   - `reviewer`: проверить, нет ли в плане скрытых предположений про модификацию OpenCode;
3. shell-скрипты поднимают оба `opencode` в отдельных tmux pane;
4. researcher и reviewer пишут свои результаты в файлы;
5. shell-скрипты отправляют main agent'у prompt прочитать оба результата;
6. main agent делает финальный синтез и пишет `PLAN.md`.

Это уже полностью соответствует ограничению "не менять OpenCode".

## 27. Failure model

Нужно заранее принять, что внешний orchestration слой иногда будет лажать.

### Возможные проблемы

- OpenCode в pane стартовал, но не понял prompt;
- агент не записал `result.json`;
- агент завис и молчит;
- shell-скрипт не туда отправил `send-keys`;
- файлы появились, но формат кривой;
- main agent проигнорировал follow-up prompt.

### Что делать

- если нет `DONE`/`FAILED` маркера в пределах таймаута — считать run stuck;
- смотреть `transcript.log` и `capture-pane`;
- retry запускать только после обновления spec/prompt;
- не считать pane exit доказательством успеха;
- считать успехом **только наличие файла `DONE`** с валидным содержимым.

### 27.1 Watchdog — обязательный компонент MVP

Без watchdog зависшие агенты и пропущенные ошибки гарантированы. Watchdog — это **не nice-to-have**, а обязательная часть MVP.

#### Что делает watchdog

Watchdog — это фоновый shell-скрипт, который периодически проверяет состояние всех активных run и реагирует на аномалии.

#### `watchdog.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

SESSION_DIR="$1"
CHECK_INTERVAL="${2:-10}"   # секунд между проверками
RUN_TIMEOUT="${3:-300}"     # секунд до признания run зависшим
PANE_SILENCE="${4:-120}"    # секунд молчания pane = подозрение на зависание

log() {
  local ts
  ts=$(date -u +%Y-%m-%dT%H:%M:%SZ)
  printf '{"ts":"%s","level":"%s","msg":"%s"}\n' "$ts" "$1" "$2" \
    >> "$SESSION_DIR/event-log.jsonl"
}

check_run() {
  local run_dir="$1"
  local run_id
  run_id=$(basename "$run_dir")

  # Уже завершён?
  [ -f "$run_dir/DONE" ] && return 0
  [ -f "$run_dir/FAILED" ] && return 0

  # Проверяем возраст run
  local created
  created=$(stat -f %m "$run_dir/spec.md" 2>/dev/null || echo 0)
  local now
  now=$(date +%s)
  local age=$(( now - created ))

  # Timeout по общему времени
  if [ "$age" -gt "$RUN_TIMEOUT" ]; then
    log "error" "run $run_id exceeded timeout (${age}s > ${RUN_TIMEOUT}s)"
    cat > "$run_dir/FAILED" <<EOF
{
  "run_id": "$run_id",
  "status": "failed",
  "reason": "watchdog timeout after ${age}s",
  "failed_at": "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
}
EOF
    return 1
  fi

  # Проверяем, жив ли pane (если записан pane_id)
  if [ -f "$run_dir/.pane_id" ]; then
    local pane_id
    pane_id=$(cat "$run_dir/.pane_id")
    if ! tmux has-session -t "$pane_id" 2>/dev/null; then
      log "error" "run $run_id: pane $pane_id is dead"
      cat > "$run_dir/FAILED" <<EOF
{
  "run_id": "$run_id",
  "status": "failed",
  "reason": "pane $pane_id died unexpectedly",
  "failed_at": "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
}
EOF
      return 1
    fi
  fi

  # Проверяем молчание pane
  if [ -f "$run_dir/transcript.log" ]; then
    local last_modified
    last_modified=$(stat -f %m "$run_dir/transcript.log" 2>/dev/null || echo 0)
    local silence=$(( now - last_modified ))
    if [ "$silence" -gt "$PANE_SILENCE" ]; then
      log "warn" "run $run_id: pane silent for ${silence}s"
    fi
  fi

  return 0
}

# Основной цикл
while true; do
  for run_dir in "$SESSION_DIR"/runs/run-*; do
    [ -d "$run_dir" ] || continue
    check_run "$run_dir" || true
  done
  sleep "$CHECK_INTERVAL"
done
```

#### Что watchdog НЕ делает

- Не убивает агентов автоматически (только ставит `FAILED` маркер).
- Не перезапускает run (это решение shell-обвязки или пользователя).
- Не вмешивается в работу main agent.

#### Как запускается

Watchdog стартует вместе с session:

```bash
# В start-session.sh добавляется:
nohup ./watchdog.sh "$SESSION_DIR" 10 300 120 &
echo $! > "$SESSION_DIR/.watchdog_pid"
```

#### Event log

Watchdog и shell-обвязка пишут события в единый журнал:

```text
.orchestrator/sessions/session-001/event-log.jsonl
```

Формат — JSONL (одна JSON-строка на событие):

```json
{"ts":"2026-03-18T12:00:00Z","level":"info","msg":"run run-001 spawned"}
{"ts":"2026-03-18T12:05:00Z","level":"info","msg":"run run-001 DONE"}
{"ts":"2026-03-18T12:06:00Z","level":"warn","msg":"run run-002: pane silent for 125s"}
{"ts":"2026-03-18T12:08:00Z","level":"error","msg":"run run-002 exceeded timeout (310s > 300s)"}
```

Этот лог используется для:
- диагностики проблем;
- session recovery (см. секцию 27.3);
- аудита того, что произошло в session.

### 27.2 Cancel и abort механизм

В текущем плане нет способа остановить конкретного сабагента или всю orchestration. Это должно быть в MVP.

#### `cancel-agent.sh` — остановка одного сабагента

```bash
#!/usr/bin/env bash
set -euo pipefail

RUN_DIR="$1"
RUN_ID=$(basename "$RUN_DIR")

# Читаем pane_id
if [ ! -f "$RUN_DIR/.pane_id" ]; then
  echo "No pane_id found for $RUN_ID" >&2
  exit 1
fi

PANE_ID=$(cat "$RUN_DIR/.pane_id")

# Убиваем pane (это убьёт процесс OpenCode внутри)
tmux kill-pane -t "$PANE_ID" 2>/dev/null || true

# Создаём маркер FAILED
cat > "$RUN_DIR/FAILED" <<EOF
{
  "run_id": "$RUN_ID",
  "status": "cancelled",
  "reason": "manually cancelled by user or orchestrator",
  "cancelled_at": "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
}
EOF

# Логируем
SESSION_DIR=$(dirname "$(dirname "$RUN_DIR")")
printf '{"ts":"%s","level":"warn","msg":"run %s cancelled"}\n' \
  "$(date -u +%Y-%m-%dT%H:%M:%SZ)" "$RUN_ID" \
  >> "$SESSION_DIR/event-log.jsonl"

echo "Run $RUN_ID cancelled."
```

#### `abort-session.sh` — остановка всей orchestration

```bash
#!/usr/bin/env bash
set -euo pipefail

SESSION_DIR="$1"
SESSION_NAME="${2:-opencode-orc}"

# Убиваем watchdog
if [ -f "$SESSION_DIR/.watchdog_pid" ]; then
  kill "$(cat "$SESSION_DIR/.watchdog_pid")" 2>/dev/null || true
fi

# Отмечаем все незавершённые run как cancelled
for run_dir in "$SESSION_DIR"/runs/run-*; do
  [ -d "$run_dir" ] || continue
  [ -f "$run_dir/DONE" ] && continue
  [ -f "$run_dir/FAILED" ] && continue

  RUN_ID=$(basename "$run_dir")
  cat > "$run_dir/FAILED" <<EOF
{
  "run_id": "$RUN_ID",
  "status": "cancelled",
  "reason": "session aborted",
  "cancelled_at": "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
}
EOF
done

# Убиваем tmux session
tmux kill-session -t "$SESSION_NAME" 2>/dev/null || true

printf '{"ts":"%s","level":"warn","msg":"session %s aborted"}\n' \
  "$(date -u +%Y-%m-%dT%H:%M:%SZ)" "$SESSION_NAME" \
  >> "$SESSION_DIR/event-log.jsonl"

echo "Session $SESSION_NAME aborted. All runs marked as cancelled."
```

#### Правила отмены

- `cancel-agent.sh` можно вызывать в любой момент для любого активного run;
- `abort-session.sh` — ядерная кнопка, убивает всё;
- после cancel main agent должен получить follow-up prompt о том, что run отменён;
- retry после cancel — новый run с новым `run_id`, а не перезапуск старого.

### 27.3 Session recovery

Если tmux session упал (reboot, crash, detach + потеря), orchestration должна уметь восстановить своё состояние.

#### Что нужно для recovery

Всё состояние orchestration хранится в файловой системе:
- `event-log.jsonl` — полная хронология событий;
- `plan.json` — какие run были запланированы;
- `DONE`/`FAILED` маркеры — какие run завершены;
- `spec.md` + `prompt.txt` — что именно было отправлено агенту.

#### `recover-session.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

SESSION_DIR="$1"
SESSION_NAME="${2:-opencode-orc}"

echo "=== Session Recovery ==="
echo "Session dir: $SESSION_DIR"
echo ""

# Статистика по run
total=0; done=0; failed=0; stuck=0

for run_dir in "$SESSION_DIR"/runs/run-*; do
  [ -d "$run_dir" ] || continue
  total=$((total + 1))
  RUN_ID=$(basename "$run_dir")

  if [ -f "$run_dir/DONE" ]; then
    done=$((done + 1))
    echo "  [DONE]   $RUN_ID"
  elif [ -f "$run_dir/FAILED" ]; then
    failed=$((failed + 1))
    reason=$(jq -r '.reason // "unknown"' "$run_dir/FAILED" 2>/dev/null || echo "unknown")
    echo "  [FAILED] $RUN_ID — $reason"
  else
    stuck=$((stuck + 1))
    echo "  [STUCK]  $RUN_ID — no DONE/FAILED marker"
  fi
done

echo ""
echo "Total: $total | Done: $done | Failed: $failed | Stuck: $stuck"

if [ "$stuck" -gt 0 ]; then
  echo ""
  echo "Stuck runs detected. Options:"
  echo "  1. Retry: re-spawn agent with same spec"
  echo "  2. Cancel: mark as FAILED and move on"
  echo "  3. Skip: resume main agent without these results"
fi
```

#### Принципы recovery

- Recovery **не перезапускает** агентов автоматически — только показывает состояние и предлагает варианты.
- Stuck run можно retry с тем же `spec.md`, но новым `run_id`.
- Main agent можно возобновить, отправив ему follow-up prompt со сводкой: какие run завершены, какие пропущены.
- `event-log.jsonl` позволяет восстановить полную картину того, что произошло до падения.

## 28. MVP без модификации OpenCode

Самый правильный MVP такой:

**Обязательные компоненты:**

- внешняя shell-обвязка (`start-session.sh`, `spawn-agent.sh`, `send-task.sh`, `resume-main.sh`, `cancel-agent.sh`, `abort-session.sh`);
- один `tmux` session;
- один main-agent pane (фиксированный, левый);
- максимум 3 одновременных subagent pane (с очередью при необходимости);
- файловый контракт: `spec.md`, `prompt.txt`, `status.json`, `handoff.md`, `result.json`, `DONE`/`FAILED` маркеры;
- `pipe-pane` в `transcript.log`;
- буферизованная отправка промптов через `paste-buffer` (не построчный `send-keys`);
- проверка готовности pane перед отправкой (`wait_for_prompt`);
- watchdog-скрипт для обнаружения зависших и упавших run;
- `event-log.jsonl` для аудита и recovery;
- follow-up prompts для main agent с `<<<ORC_FOLLOW_UP>>>` разделителями;
- `plan.json` как файловый интерфейс для main-agent-led планирования (не парсинг pane output);
- `recover-session.sh` для диагностики после сбоев.

**Не входит в MVP (отложено на v2):**

- custom roles и skill `orchestrator-role-factory`;
- автоматический retry зависших run;
- multi-session режим (вариант C из секции 10);
- DAG-based зависимости с параллельным исполнением (в MVP — линейная очередь для depends_on).

Этого уже достаточно, чтобы main agent реально мог:

- инициировать сабагентов через `plan.json`;
- дождаться их завершения (watchdog + `DONE`/`FAILED` маркеры);
- получить от них инфу через follow-up prompt;
- продолжить работу в той же живой сессии;
- при ошибке — увидеть причину и решить: retry или пропустить.

## 28.1 Пример shell/tmux workflow

Ниже не production-ready реализация, а конкретный сценарий, как это может работать на практике через `.sh`.

### `start-session.sh`

Поднимает tmux session и main agent:

```bash
#!/usr/bin/env bash
set -euo pipefail

SESSION="opencode-orc"
WORKDIR="$(pwd)"

tmux new-session -d -s "$SESSION" -n main "bash"
tmux send-keys -t "$SESSION":main.0 "cd $WORKDIR && opencode" Enter

# Делим layout так, чтобы левый pane был главным.
tmux split-window -t "$SESSION":main.0 -h -p 70 "bash"
tmux select-pane -t "$SESSION":main.0
```

### `spawn-agent.sh`

Создает pane под сабагента и запускает там `opencode`:

```bash
#!/usr/bin/env bash
set -euo pipefail

SESSION="$1"
TARGET_WINDOW="$2"
RUN_ID="$3"

# Предполагается, что pane 0 слева = orchestrator, а pane 1 справа = worker zone.
tmux select-pane -t "$SESSION":"$TARGET_WINDOW".1
tmux split-window -t "$SESSION":"$TARGET_WINDOW".1 -v "bash"
PANE_ID=$(tmux display-message -p -t "$SESSION":"$TARGET_WINDOW" '#{pane_id}')
tmux send-keys -t "$PANE_ID" "opencode" Enter

printf '%s\n' "$PANE_ID"
```

### `send-task.sh`

Отправляет агенту bootstrap prompt через буферизованную вставку (см. секцию 8.3):

```bash
#!/usr/bin/env bash
set -euo pipefail

PANE_ID="$1"
RUN_ID="$2"
SID="${3:-session-001}"
RUN_DIR=".orchestrator/sessions/$SID/runs/$RUN_ID"

# Формируем промпт и сохраняем в файл (аудит + retry)
cat > "$RUN_DIR/prompt.txt" <<EOF
Прочитай файл $RUN_DIR/spec.md.

Затем:
1. Выполни задачу строго в рамках spec.
2. Если уместно, обновляй $RUN_DIR/status.json.
3. По завершении запиши в таком порядке:
   - $RUN_DIR/result.json
   - $RUN_DIR/handoff.md
   - $RUN_DIR/DONE (JSON с run_id, status, files, completed_at)
4. Не пиши финальный ответ пользователю. Пиши результат для main agent.
EOF

# Ждём готовности pane
wait_for_prompt "$PANE_ID" 60 || { echo "Pane not ready" >&2; exit 1; }

# Буферизованная отправка
tmux set-buffer -b task "$(cat "$RUN_DIR/prompt.txt")"
tmux paste-buffer -b task -t "$PANE_ID"
tmux send-keys -t "$PANE_ID" Enter

# Сохраняем pane_id для watchdog
echo "$PANE_ID" > "$RUN_DIR/.pane_id"
```

### `resume-main.sh`

Возвращает результат сабагента в main agent через буферизованную вставку:

```bash
#!/usr/bin/env bash
set -euo pipefail

MAIN_PANE="$1"
RUN_ID="$2"
SID="${3:-session-001}"
RUN_DIR=".orchestrator/sessions/$SID/runs/$RUN_ID"

# Определяем статус
if [ -f "$RUN_DIR/DONE" ]; then
  ROLE=$(jq -r '.role // "unknown"' "$RUN_DIR/DONE" 2>/dev/null || echo "unknown")
  PROMPT=$(cat <<EOF
<<<ORC_FOLLOW_UP>>>
Завершен subagent run \`$RUN_ID\` (роль: $ROLE).
Статус: completed.

Прочитай результаты:
- $RUN_DIR/handoff.md
- $RUN_DIR/result.json

Используй это как входной контекст.
Если нужно, обнови plan.json с новыми задачами или подготовь финальный ответ.
<<<END_ORC_FOLLOW_UP>>>
EOF
)
elif [ -f "$RUN_DIR/FAILED" ]; then
  REASON=$(jq -r '.reason // "unknown"' "$RUN_DIR/FAILED" 2>/dev/null || echo "unknown")
  PROMPT=$(cat <<EOF
<<<ORC_FOLLOW_UP>>>
Subagent run \`$RUN_ID\` завершился с ошибкой.
Причина: $REASON.

Прочитай $RUN_DIR/FAILED для деталей.
Реши: нужен ли retry (запиши новый run в plan.json) или можно продолжить без этого результата.
<<<END_ORC_FOLLOW_UP>>>
EOF
)
fi

# Сохраняем follow-up промпт для аудита
echo "$PROMPT" > "$RUN_DIR/followup-prompt.txt"

# Ждём готовности main pane
wait_for_prompt "$MAIN_PANE" 120 || { echo "Main pane not ready" >&2; exit 1; }

# Буферизованная отправка
tmux set-buffer -b followup "$PROMPT"
tmux paste-buffer -b followup -t "$MAIN_PANE"
tmux send-keys -t "$MAIN_PANE" Enter
```

### `request-review.sh`

Если задача кодовая, reviewer получает отдельный prompt на проверку diff:

```bash
#!/usr/bin/env bash
set -euo pipefail

REVIEW_PANE="$1"
RUN_DIR="$2"

PROMPT=$(cat <<EOF
Посмотри текущий git diff перед коммитом.
Проверь, соответствует ли diff задаче, нет ли лишних изменений и рисков.
Запиши вывод в $RUN_DIR/handoff.md и $RUN_DIR/result.json.
В конце создай $RUN_DIR/DONE.
EOF
)

echo "$PROMPT" > "$RUN_DIR/prompt.txt"

wait_for_prompt "$REVIEW_PANE" 60 || { echo "Review pane not ready" >&2; exit 1; }

tmux set-buffer -b review "$PROMPT"
tmux paste-buffer -b review -t "$REVIEW_PANE"
tmux send-keys -t "$REVIEW_PANE" Enter
```

### Пример живого цикла

1. `start-session.sh` поднимает main agent.
2. левый pane закрепляется как единственная точка общения с orchestrator/main agent.
3. main agent получает задачу и выдает `SUBAGENT_PLAN`.
4. shell-обвязка для каждого пункта вызывает `spawn-agent.sh` только в правой worker-zone.
5. затем вызывает `send-task.sh`, чтобы дать каждому сабагенту его `spec.md`.
6. shell-обвязка ждет `handoff.md`/`result.json`.
7. после готовности вызывает `resume-main.sh` и отправляет результат в левый pane.
8. main agent в своей исходной левой pane продолжает писать.
9. если есть кодовые изменения, дополнительно вызывается `request-review.sh` для reviewer pane.

## 28.2 Защита от prompt injection и prompt confusion

Все промпты передаются как plain text через `send-keys` / `paste-buffer`. Если в контексте задачи пользователя есть текст, похожий на служебные конструкции (`SUBAGENT_PLAN`, инструкции агенту, маркеры формата), main agent может интерпретировать это неправильно.

### Меры защиты

#### 1. Разделители для служебных блоков

Все служебные конструкции (план, follow-up, bootstrap prompt) должны быть обёрнуты в уникальные разделители, которые крайне маловероятно встретить в пользовательском тексте:

```text
<<<ORC_FOLLOW_UP>>>
Сабагент run-001 завершил работу.
Прочитай файлы: ...
<<<END_ORC_FOLLOW_UP>>>
```

#### 2. Промпты агентам — из файлов, не inline

Вместо того чтобы слать длинные инструкции через `send-keys`, shell-обвязка записывает промпт в файл и отправляет агенту короткую команду:

```text
Прочитай файл .orchestrator/sessions/session-001/runs/run-001/prompt.txt и выполни инструкции.
```

Это минимизирует поверхность атаки: в pane попадает только путь к файлу, а не весь контент.

#### 3. Валидация plan.json

Shell-обвязка должна валидировать `plan.json` перед исполнением:
- только допустимые роли из предустановленного пула (для MVP);
- `run_id` соответствует паттерну `run-NNN`;
- пути `output_files` находятся внутри `.orchestrator/`;
- нет неожиданных полей, которые могут быть инъекцией.

```bash
validate_plan() {
  local plan="$1"
  local valid_roles='["researcher","explorer","reviewer","summarizer","verifier"]'

  # Проверяем, что все роли из допустимого пула
  local bad_roles
  bad_roles=$(jq -r --argjson valid "$valid_roles" \
    '.tasks[].role | select(. as $r | $valid | index($r) | not)' "$plan")

  if [ -n "$bad_roles" ]; then
    echo "Invalid roles in plan: $bad_roles" >&2
    return 1
  fi

  # Проверяем, что output_files внутри .orchestrator/
  local bad_paths
  bad_paths=$(jq -r '.tasks[].output_files[] | select(startswith(".orchestrator/") | not)' "$plan")

  if [ -n "$bad_paths" ]; then
    echo "Invalid output paths: $bad_paths" >&2
    return 1
  fi

  return 0
}
```

## 29. Что НЕ надо делать

- не проектировать новые встроенные режимы OpenCode;
- не рассчитывать на изменения в коде OpenCode;
- не полагаться на внутренние API OpenCode, если их нет;
- не использовать pane text как единственный формат возврата результата;
- не делать слишком умную shell-обвязку, которая фактически заменяет main agent;
- не спавнить слишком много одинаковых сабагентов без явной пользы;
- не спавнить больше 3 одновременных subagent pane в MVP (использовать очередь);
- не реализовывать custom roles в MVP (отложить на v2);
- не слать длинные промпты через `send-keys` построчно (использовать `paste-buffer`).

## 30. Итоговая рекомендация

Лучший вариант orchestration для OpenCode TUI при данном ограничении такой:

- брать **несколько обычных экземпляров OpenCode**;
- запускать их **в отдельных tmux pane/window**;
- фиксировать **самый левый pane** как постоянную orchestrator/main-agent зону;
- использовать **правую часть layout** как динамическую worker-zone для сабагентов;
- держать **внешние `.sh`-скрипты** как тонкий слой управления;
- передавать задачи через **`tmux send-keys` + `spec.md`**;
- собирать результаты через **`handoff.md`/`result.json`** в общем workspace;
- отправлять main agent'у **новые follow-up prompts**, чтобы он читал результаты и продолжал reasoning;
- сохранять main agent как одну живую непрерывную сессию, которая после output сабагентов может дальше писать, синтезировать и вести задачу до конца.

Если совсем коротко:

**main agent логически решает, какие нужны сабагенты; tmux физически запускает эти экземпляры OpenCode; `.sh`-скрипты маршрутизируют `send-keys` и handoff; `spec.md` задает профессию и задачу агента; main agent после output сабагентов не останавливается, а продолжает писать в той же живой сессии, читая handoff/result артефакты и двигая задачу дальше.**

## 31. Мини-раздел: ожидаемое поведение системы

Ниже поведение системы в самом коротком и прикладном виде.

- пользователь пишет задачу main agent'у в TUI;
- main agent начинает работать сам и при необходимости формирует `SUBAGENT_PLAN`;
- shell-скрипты через `tmux` поднимают нужных сабагентов и отправляют им задания через `send-keys`;
- самый левый pane всегда остается за orchestrator/main agent, а все правые pane используются под временных помощников;
- `spec.md` определяет профессию агента, его ограничения и текущую работу;
- сабагенты выполняют свои узкие задачи и оставляют `handoff.md`/`result.json`;
- shell-скрипты возвращают их output обратно main agent'у через follow-up prompt;
- main agent в той же живой сессии продолжает писать дальше, а не начинает работу заново;
- если задача кодовая, reviewer перед коммитом смотрит `git diff` и проверяет корректность изменений;
- для пользователя все выглядит как работа одного основного агента, который временно привлекает помощников и потом продолжает мысль без разрыва.
